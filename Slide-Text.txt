SLIDE 2 - Introduction: what is SATD
============================================================
Heading: Developers admit shortcuts in writing - that admission is SATD

- SATD means Self-Admitted Technical Debt: the developer writes that some part is not done properly yet.
- Examples: TODO fix later. This is a hack. Tests are missing. Docs are outdated.
- Found in 4 places: code comments, issues, commit messages, pull requests.
- Labels we use: Not-SATD, C/D (code/design), REQ (requirement), TES (test), DOC (documentation).

SLIDE 3 - Introduction: why it matters now
============================================================
Heading: Fast code makes more debt, and manual review cannot keep up

- Shortcut taken, small note written, nobody tracks it, later it becomes bugs and slow changes.
- Large projects produce more text than any team can read by hand.
- Different debt types need different fixes, so finding is not enough, we must also type it.
- AI assistants raise the stakes: 3-5x lines added in the first month (Cursor study), review time up 91% (Faros).

============================================================
SLIDE 4 - Related Works 1: the AI productivity puzzle
============================================================
Heading: AI writes faster, but delivery does not always follow

- Vibe coding survey, Ge et al. 2025 (A Survey of Vibe Coding with Large Language Models): success depends on context engineering and verification, not raw agent skill.
- Productivity paradox review, Singh 2025 (From Code Generation to Code Verification: Explaining and Mitigating the AI Productivity Paradox in Software Engineering): narrow tasks +55.8% speed, but realistic OSS trial -19% (METR 2025).
- High AI adoption: +21% tasks done, but +91% review time and +154% PR size (Faros AI 2025).
- Our takeaway: the bottleneck moved from writing code to verifying it.

============================================================
SLIDE 5 - Related Works 2: what fast code costs
============================================================
Heading: Speed now can mean complexity and flaws later

- Cursor study, He et al. 2026 (Speed at the Cost of Quality: How Cursor AI Increases Short-Term Velocity and Long-Term Complexity in Open-Source Projects) (MSR 2026): warnings +30%, complexity +41% and persistent; debt later slows velocity.
- Veracode 2025 (GenAI Code Security Report: Assessing the Security Performance of Newer LLMs): about 45% of LLM code introduces the target flaw; only GPT-5 family clearly above ~70%.
- Slopsquatting, Park / Trend Micro 2025 (Slopsquatting: Hallucination in Coding Agents and Vibe Coding): agents still invent package names; MCP checks halve it, never zero it.
- Our takeaway: generated code needs debt and security triage by default.

============================================================
SLIDE 6 - Related Works 3: debt and correctness thinking
============================================================
Heading: Debt is not only in code - it is in understanding and intent

- GIST study, Al Mujahid & Imran 2026 (TODO: Fix the Mess Gemini Created: Towards Understanding GenAI-Induced Self-Admitted Technical Debt): 81 AI-linked SATDs; design 40.7%, requirement 21%, test 21%; AI as catalyst 42%.
- Triple debt, Storey 2026 (From Technical Debt to Cognitive and Intent Debt: Rethinking Software Health in the Age of AI): AI may cut code debt while growing cognitive debt (lost understanding) and intent debt (lost goals).
- HoarePrompt, Bouras et al. 2025 (HoarePrompt: Structural Reasoning About Program Correctness in Natural Language): step-by-step state reasoning beats naive prompting for correctness checks.
- Baseline for our numbers: Sutoyo, Avgeriou & Capiluppi 2024 (Deep Learning and Data Augmentation for Detecting Self-Admitted Technical Debt) (BiLSTM for finding, BERT for typing, + AugGPT).

============================================================
Heading: Our 4 simple questions

- Q1: Can our simple method find SATD? (like BiLSTM does)
- Q2: Can it tell the SATD type? (like BERT does) - types are code/design, requirement, test, doc
- Q3: Do the answers change if we change the data?
- Q4: Which matters more - the embedding model or the classifier?

In simple words: does a cheap method work, and when does it break?

SLIDE 9 - Methodology 2: our steps
============================================================
Heading: Our steps are the same every time - that is why the test is fair

- Take the text (a comment, issue, commit, or pull request).
- Turn it into numbers using a ready-made model. We do not train this part.
- Use a small classifier on those numbers. Main one is XGBoost.
- Step 1: is it SATD or not? Step 2: if yes, what type?

SLIDE 15 - Results 3: what many real issues told us
============================================================
Heading: Real issues show more debt in descriptions, and the classifier mattered most

- 458k new issues: title 38% SATD, description 59% SATD, both together 55% SATD.
- So the description has about 20% more debt signal than the title alone.
- With XGBoost: BGE-M3 0.926, Qwen3 0.925, E5 0.921 - almost same.
- With simple LogReg: score drops to about 0.85. So the classifier matters more than which embedding we pick.

SLIDE 16 - Challenges and Limitations
============================================================
Heading: What was hard and what we do not claim

- Cleaning 31 files and fixing labels took the most time.
- Our GPU was small, so long texts were cut to 256 pieces. 16% were cut.
- In Setup A, similar texts can appear in both train and test by mistake.
- The 458k issues have no correct answer set, so we cannot say how accurate it is there.
- BGE-M3 code is not saved in the repo. Short commits are still the hardest.

Heading: What we learned and what we will do next

What we learned:
